# C/C++ (hard). Память, переполнение, немного C++

Здесь - то, что связывает C с pwn и реверсом: как лежит память, почему длинный ввод ломает
программу, и чем отличается C++. Всё только для **понимания** (эксплойтов тут нет - они в `09-pwn`).

---

## 1. Массив и указатель - почти одно и то же

Имя массива само по себе - это **адрес его первого элемента**. Поэтому две записи ниже равнозначны:

```c
#include <stdio.h>
int main(void) {
    char s[] = "flag";
    char *p = s;                        // p = адрес начала массива
    printf("%c%c\n", s[1], *(p + 1));   // s[1] и *(p+1) - одно и то же -> ll
    return 0;
}
```

💡 Правило чтения декомпилятора: `*(p + i)` - это просто `p[i]`. Ghidra часто пишет обращения к
строкам именно в виде `*(char *)(param_1 + i)` - читай как "i-й символ строки `param_1`".

## 2. Как лежит память и почему это важно

Локальные переменные функции лежат на **стеке** - вплотную друг к другу. Если писать в массив больше,
чем он вмещает, лишние байты уходят на соседей. Это и есть переполнение буфера.

```c
#include <stdio.h>
#include <string.h>
int main(void) {
    int  is_admin = 0;      // сосед буфера
    char buf[8];            // место ровно на 8 байт
    strcpy(buf, "AAAAAAAAAAAA");   // 12 'A' - 8 в buf, лишние 4 ушли в соседа
    printf("is_admin = %d\n", is_admin);   // уже не 0!
    if (is_admin) printf("flag{overflow_changed_me}\n");
    return 0;
}
```

Собрать без защиты стека и запустить:

```bash
gcc -fno-stack-protector -o prog prog.c && ./prog
# is_admin = 1094795585
# flag{overflow_changed_me}
```

Почему `1094795585`? Это четыре байта `'A'` (`0x41`), слипшиеся в одно число: `0x41414141`. Было `0`,
стало "мусор из наших букв" - проверка `if (is_admin)` сработала.

⚠️ Точное число и даже сам факт срабатывания зависят от компилятора, флагов и порядка переменных в
памяти - это **демонстрация идеи**, а не готовый приём. Современный `gcc` по умолчанию ставит защиту
(stack protector), поэтому для наглядности её выше отключили (`-fno-stack-protector`).

🔺 В реальных pwn-задачах затирают не соседнюю переменную, а **адрес возврата функции** - и заставляют
программу прыгнуть куда нужно. Это тема `09-pwn/hard.md`; здесь важно понять фундамент: **длинный
ввод залезает на то, что лежит дальше в памяти**.

## 3. Опасные функции (их ищут в реверсе и pwn)

Переполнение возможно, когда ввод читают **без проверки длины**:

```c
char buf[8];
gets(buf);              // ОПАСНО: читает сколько угодно, границы не знает
strcpy(buf, src);       // ОПАСНО: копирует src целиком, даже если не влезает
scanf("%s", buf);       // ОПАСНО: тот же %s без ограничения длины
```

Безопасные версии ограничивают длину: `fgets(buf, sizeof(buf), stdin)`, `strncpy`, `scanf("%7s", ...)`.

💡 Увидел в коде (или в Ghidra) `gets`, `strcpy`, `scanf("%s")` и рядом маленький `char buf[...]` -
это красный флаг: скорее всего, тут и есть переполнение. В `09-pwn` именно это и ищут.

## 4. gcc vs g++ и немного C++

C++ - это надстройка над C: почти весь C там работает, плюс добавлены строки-объекты, потоки
ввода-вывода, классы. Файлы `.cpp`, компилятор `g++`.

```cpp
#include <iostream>     // вместо stdio.h
#include <string>
int main() {
    std::string s = "flag";   // строка-объект, сама следит за длиной
    s += "{cpp}";                 // к строке можно прибавлять
    std::cout << s << std::endl;  // cout вместо printf, << "подаёт" данные -> flag{cpp}
    return 0;
}
```

```bash
g++ -o prog prog.cpp && ./prog     # -> flag{cpp}
```

`std::cout << x` печатает `x`; `std::endl` - перевод строки. Арифметика и типы - те же, что в C:

```cpp
#include <iostream>
int main() {
    int x = 21;
    std::cout << "flag{" << x * 2 << "}" << std::endl;   // -> flag{42}
    return 0;
}
```

🔺 Зачем это на реверсе: C++-бинарники читать сложнее - в Ghidra будут вызовы вроде
`std::__cxx11::basic_string...` и "лишние" служебные функции (конструкторы, деструкторы). Опознать
C++ помогает `strings`: там мелькают `std::`, `__cxx`, `basic_string`. Тактика та же - найти
сравнение ввода с эталоном, остальное пролистать.

## 5. Как исходник превращается в псевдокод

Один и тот же код в исходнике и в декомпиляторе выглядит по-разному. Полезно держать в голове
соответствия:

| В исходнике C | Что увидишь в Ghidra |
|---|---|
| `char buf[16]` | `char local_18 [16]` (имя по смещению на стеке) |
| имя переменной `pass` | `local_18`, `param_1`, `iVar1` (имена потеряны) |
| `s[i]` | `*(char *)(param_1 + i)` |
| `if (strcmp(a,b)==0)` | вызов `strcmp`, затем проверка результата на `0` |
| `for (i=0; i<n; i++)` | метка + условный переход назад (цикл) |
| строковый литерал `"s3cret"` | строка в секции данных, видна в Defined Strings |

```c
char pass[16];
scanf("%15s", pass);
if (strcmp(pass, "s3cret") == 0) printf("flag{ok}\n");   // пароль прямо в коде
```

Такой код в декомпиляторе - это "прочитать ввод -> `strcmp` с `"s3cret"` -> если равно, печать
флага". Имена переменных пропадут, но **логика сохранится**, а литерал `"s3cret"` часто виден прямо
в строках бинарника. Это ровно то, что ты будешь распутывать в `08-reverse`.

🎯 **Тренировка (hard).** Собери программу из п. 5 (`gcc -o prog prog.c`), найди строку-пароль через
`strings prog | grep -i secret`, введи её и получи флаг. Потом открой `prog` в Ghidra (см.
`08-reverse/ghidra.md`) и найди в псевдокоде тот самый `strcmp` - сопоставь исходник и декомпиляцию.
